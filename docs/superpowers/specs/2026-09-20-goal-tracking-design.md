# 通用目标与进展追踪设计

日期：2026-09-20

状态：待用户审阅

适用项目：青笺个人事务

## 1. 背景与决策

用户需要根据《研究生综合素质学分模块设定（2022.10）》持续记录个人完成情况，但该需求不应演变成一个只服务于综合素质学分的新功能模块。毕业准备、考试复习、证书申请等长期结果也可能由多项固定任务或动态累计记录共同达成。

本设计新增一次通用的“目标”能力。综合素质要求是一个目标模板和目标实例，不是独立业务模块。

目标由若干条件块组成：

- 清单型条件块：预先列出清单项，逐项完成。
- 计数型条件块：把实际完成事实记录到分类中，按累计数量、分类最低数量和覆盖分类数判断是否达标。

一个目标只有在所有条件块都达标时，达成结果才是“已达成”。

## 2. 目标与非目标

### 2.1 目标

- 用同一套模型表达固定清单、动态累计以及二者混合的目标。
- 采用表格为主的交互，清楚回答“已经完成什么”和“还缺什么”。
- 让进展记录保持轻量：默认只需内容、完成日期、条件块和统计分类。
- 根据原始记录实时计算达成结果，避免手工维护汇总值。
- 与现有信息、事务、待办保持清晰边界，不强制关联。
- 提供全日制研究生综合素质要求模板，同时允许用户填写附件未列出的活动名称。

### 2.2 首版非目标

- 不自动把目标内容同步到待办、信息或事务。
- 不保存证明材料，不提供审核流程。
- 不提供任意公式语言、权重或主观完成百分比。
- 不提供提醒、截止日期、多人协作、模板共享或模板市场。
- 不把学分规则写成专用页面或专用数据表。

## 3. 领域模型

### 3.1 目标

目标描述最终要达成的结果，例如“完成研究生综合素质要求”或“准备毕业”。目标拥有名称、可选说明、创建与更新时间，以及用户控制的生命周期。

生命周期只有“进行中”和“已归档”。“未达成”与“已达成”是系统按当前条件计算出的达成结果，不与生命周期混为一个字段。已达成的目标可以继续保留在进行中，也可以由用户归档。

空目标没有条件块，必须视为未达成。

### 3.2 条件块

一个目标包含一个或多个有序条件块。每个条件块只能是以下一种类型：

- 清单型：包含若干清单项，所有清单项完成后达标。
- 计数型：包含若干统计分类和规则，由进展记录计算是否达标。

所有条件块都达标时，目标才达成。

### 3.3 清单项

清单项用于表达预先明确的完成条件，例如“提交论文初稿”。清单项包含名称、显示顺序和可空的完成日期。

勾选清单项时默认把当天记为完成日期；用户可以修改日期。取消勾选时清除完成日期。清单项不是待办，不自动出现在待办清单中。

### 3.4 统计分类与计数规则

计数型条件块可以组合以下规则：

- 条件块累计量至少达到指定值。
- 指定统计分类的累计量至少达到各自最低值。
- 达到分类最低值的统计分类数量至少达到指定值。

每个条件块设置一个显示单位，默认是“次”。进展记录的数量默认是 1；在确有需要的目标中可使用小时、页、篇等其他单位。数量必须大于 0。

系统不提供任意逻辑表达式。首版只组合以上三类规则，以保证配置可理解、计算可验证。

### 3.5 进展记录

进展记录表示已经发生并能贡献目标进度的一次完成事实，包含：

- 完成内容；
- 完成日期；
- 所属计数型条件块；
- 所属统计分类；
- 数量，默认 1。

进展记录不表示计划中的活动。未来日期不能作为完成日期。

统计结果始终从有效进展记录计算，不额外持久化“当前总数”等派生值。修改或删除记录后立即重新计算目标；原先已达成的目标可能重新变为未达成。

## 4. 达标算法

### 4.1 清单型条件块

当且仅当条件块至少包含一个清单项，并且所有清单项都有完成日期时，条件块达标。

### 4.2 计数型条件块

对每个有效统计分类计算进展记录数量之和 `category_amount`，再计算所有有效分类之和 `total_amount`。

计数型条件块同时满足以下已配置规则时达标：

1. `total_amount` 不小于条件块最低累计量；
2. 所有标记为必选的分类均达到各自最低量；
3. 达到自身最低量的分类数不小于最少覆盖分类数。

未配置的规则不参与判断。计数型条件块必须至少包含一个有效分类，并且至少配置一项约束，否则视为配置无效而不是自动达标。

### 4.3 目标

目标至少包含一个有效条件块，并且所有条件块都达标时，达成结果为“已达成”；其他情况均为“未达成”。

不保存主观百分比。界面显示真实条件，例如“累计 6/8 次”和“覆盖 2/3 类”，避免把不同性质的规则压缩成误导性的单一百分比。

## 5. 表格交互设计

### 5.1 我的目标列表

侧边栏只增加一个通用入口“我的目标”。列表包含：

| 列 | 内容 |
| --- | --- |
| 目标 | 目标名称 |
| 条件概览 | 清单项数、计数型条件块数等简要结构 |
| 当前进度 | 最关键的未满足条件，或“全部条件已满足” |
| 达成结果 | 未达成或已达成，由系统计算 |
| 生命周期 | 进行中或已归档，由用户控制 |
| 最近更新 | 最近一次结构或进展变更时间 |

默认显示进行中的目标，可以切换查看已归档目标。

### 5.2 目标详情页

页面顶部显示目标名称、达成结果和每个条件块的简明摘要。主体根据条件块类型显示两类表格。

达成条件表回答“还缺什么”：

| 条件块 | 分类或清单项 | 要求 | 当前 | 结果 |
| --- | --- | ---: | ---: | --- |
| 核心素质 | 理想信念 | 至少 1 次 | 2 次 | 已满足 |
| 核心素质 | 合计 | 至少 8 次 | 6 次 | 还差 2 次 |
| 素质提升 | 覆盖分类 | 至少 3 类 | 2 类 | 还差 1 类 |

进展记录表回答“已经完成什么”：

| 完成日期 | 完成内容 | 条件块 | 统计分类 | 数量 | 操作 |
| --- | --- | --- | --- | ---: | --- |
| 2026-09-15 | 研究生篮球赛 | 素质提升 | 强身健体 | 1 次 | 编辑、删除 |

清单型条件块直接显示清单：

| 清单项 | 状态 | 完成日期 |
| --- | --- | --- |
| 提交论文初稿 | 已完成 | 2026-09-10 |
| 完成预答辩 | 未完成 | - |

一个目标同时含有两类条件块时，两类表格都显示。窄屏下每一行转换为字段顺序一致的卡片，不要求用户横向滚动完成主要操作。

### 5.3 日常录入

新增进展记录默认只展示完成内容、完成日期、条件块和统计分类。数量默认为 1，仅当用户展开“更多”或条件块单位不是“次”时显示。

附件列出的活动可以作为活动名称建议，但输入框始终允许自定义内容。建议项只帮助填写，不参与达标计算。

### 5.4 目标结构编辑

目标编辑器分为基本信息与条件配置。新增条件块时先选择“清单型”或“计数型”，再显示对应字段。

修改规则前展示重新计算后的影响。已有进展引用的统计分类不能直接删除；用户必须先把记录移动到其他分类或删除记录。首版不引入“停用但继续计数”这种中间状态，避免同一分类在录入、展示和计算中产生三种不同解释。

## 6. 与现有对象的边界

| 对象 | 核心问题 | 与目标的关系 |
| --- | --- | --- |
| 信息 | 我收到了什么？ | 活动通知仍可保存为信息 |
| 事务 | 有什么事情需要持续办理？ | 必要时独立建立事务 |
| 待办 | 我接下来具体做什么？ | 可以另建待办，目标不依赖待办状态 |
| 目标 | 为达成长期结果还缺什么？ | 汇总条件和已完成事实 |
| 进展记录 | 我已经完成了什么？ | 只在事实发生后贡献目标进度 |

首版没有跨对象外键或自动同步。后续若重复录入成为明确痛点，可以增加“将事务记为目标进展”等快捷动作，但快捷动作仍然创建独立进展记录，不让目标结果依赖事务的可变状态。

## 7. 数据结构

建议新增以下关系表：

### 7.1 `goals`

- `id`
- `user_id`
- `title`
- `description`，可空
- `archived_at`，可空
- `created_at`
- `updated_at`

### 7.2 `goal_blocks`

- `id`
- `goal_id`
- `kind`：`checklist` 或 `quota`
- `title`
- `unit_label`，计数型默认“次”
- `minimum_total`，可空
- `minimum_distinct_categories`，可空
- `position`

清单型条件块不得设置计数规则字段；计数型条件块不得包含清单项。

### 7.3 `goal_checklist_items`

- `id`
- `block_id`
- `title`
- `completed_on`，可空
- `position`

### 7.4 `goal_categories`

- `id`
- `block_id`
- `name`
- `minimum_amount`，默认 1
- `is_required`，默认否
- `position`

### 7.5 `goal_progress_entries`

- `id`
- `block_id`
- `category_id`
- `title`
- `completed_on`
- `amount`，默认 1
- `created_at`
- `updated_at`

`user_id` 由目标所有权传递。所有读取和写入都必须从当前用户拥有的目标开始验证，不能只凭子对象 ID 操作。

## 8. 服务端与前端边界

后端新增 `backend/goals`，沿用现有模块的 `models.py`、`schemas.py`、`service.py`、`router.py` 分层。达标计算集中在服务层，路由只负责认证、输入和响应。

前端新增 `frontend/src/features/goals`，包含目标列表、目标详情、目标编辑和状态管理。工作台只新增一个“我的目标”入口。

首版模板采用后端版本化的内置配置，不新增通用模板编辑器或模板数据表。创建目标时，服务层把模板完整复制到上述目标、条件块和分类表中；复制完成后，该目标与模板版本之间不再保持运行时依赖。

读取目标详情时，服务端一次返回目标结构、原始记录和计算摘要。新增、修改或删除清单状态与进展记录后，响应包含最新摘要，使所有客户端使用同一套规则结果。

结构修改和重新计算在同一数据库事务中完成。任何校验失败都不保留部分更改。

## 9. 全日制研究生综合素质模板

模板来源为用户提供的《研究生综合素质学分模块设定（2022.10）》。附件内容只作为规则与建议项来源。

从模板创建目标时深拷贝模板结构。以后修改模板不会静默改变已经创建的目标。

### 9.1 核心素质

计数型条件块“核心素质”：

- 最低累计量：8 次；
- 最少覆盖分类数：4；
- 4 个分类全部必选，各至少 1 次。

| 统计分类 | 建议活动名称 |
| --- | --- |
| 理想信念 | 新生引航工程系列活动；爱国主义教育；主题党、团日活动；青年大学习 |
| 科学道德 | 研究生科学道德与学风建设主题教育；学术论坛系列讲座 |
| 爱校荣校 | “知校史、明校情、铸校魂”校园行；导学文化建设活动；学校成就展参观活动 |
| 安全法纪 | 入学教育；日常安全教育 |

### 9.2 素质提升

计数型条件块“素质提升”：

- 最低累计量：3 次；
- 最少覆盖分类数：3；
- 8 个分类均为可选分类，各分类达到 1 次后计入覆盖数。

| 统计分类 | 建议活动名称 |
| --- | --- |
| 学术科创 | 研究生创新创业展；挑战杯校内赛等双创赛事；科技创新沙龙；研究生学科竞赛 |
| 生涯规划 | 研究生就业指导讲座、沙龙；模拟面试大赛等实践活动 |
| 强身健体 | 研究生体育竞技赛事；群众性体育活动 |
| 心理健康 | 心理健康节系列活动 |
| 文化艺术 | 艺馨杯文艺汇演；研究生迎新、毕业晚会；五月鲜花合唱比赛；高雅艺术进校园活动；歌手大赛 |
| 志愿服务 | “志愿北京”平台累计志愿服务满 10 小时 |
| 社会实践 | 假期社会实践专项；研究生挂职锻炼；大学生实习“扬帆计划”；考核合格的助教助管工作 |
| 理论精进 | 研究生党员骨干培训班；研究生宣讲团；鸿雁讲堂累计参加 3 场及以上 |

附件允许学院增加自定项目，所以建议活动不形成封闭枚举。

“志愿服务满 10 小时”和“鸿雁讲堂参加 3 场及以上”带有自身门槛。为避免把尚未满足门槛的零散参与过早计入整体“次数”，首版采用保守解释：用户达到门槛后新增一条数量为 1 的合格进展记录。该工具是个人记录，不替代学院的正式认定；学院解释不同时，用户可以编辑目标规则与记录方式。

## 10. 校验与安全行为

- 目标、条件块、清单项、分类和进展记录均执行当前用户所有权校验。
- 标题和名称去除首尾空白后不能为空，并设置与现有项目一致的合理长度上限。
- 完成日期不得晚于服务端当前日期。
- 进展数量必须为正数。
- 进展记录只能引用同一计数型条件块下的有效分类。
- 清单项只能属于清单型条件块；统计分类和进展记录只能属于计数型条件块。
- 修改或删除进展记录后重新计算达成结果。
- 删除会改变达成结果的记录前，前端明确提示影响。
- 有历史内容的目标优先归档而不是永久删除；首版只允许永久删除没有清单完成状态和进展记录的空目标。
- 保存失败时保留前端草稿，并允许重试；未保存编辑沿用现有工作台的离开保护方式。

## 11. 测试策略

### 11.1 规则单元测试

- 核心素质覆盖 4 类但总计只有 7 次，结果未达成。
- 核心素质总计达到 8 次但缺少一个必选分类，结果未达成。
- 素质提升有 3 条记录但都在同一分类，覆盖数只有 1，结果未达成。
- 素质提升覆盖 3 类且总计 3 次，条件块达成。
- 修改数量或删除记录后，已达成条件块可以退回未达成。
- 空条件块和无约束计数块不能自动达标。
- 混合目标必须同时满足清单型和计数型条件块。

### 11.2 API 与权限测试

- 创建、读取、修改、归档目标。
- 配置两种条件块并校验不允许的字段组合。
- 勾选和取消清单项时正确维护完成日期。
- 新增、编辑和删除进展记录后返回最新摘要。
- 不允许跨账号读取或修改任何目标子对象。
- 未来完成日期、非正数量和跨条件块分类引用均被拒绝。
- 结构修改失败时不产生部分写入。

### 11.3 前端测试

- 目标列表正确显示达成结果与生命周期。
- 达成条件表同时显示总量缺口和分类缺口。
- 普通新增记录默认隐藏数量字段并使用 1。
- 删除记录前显示达成结果可能变化的提示。
- 规则编辑预览修改后的结果。
- 未保存结构编辑触发现有离开保护。
- 窄屏卡片保留桌面表格的全部核心信息和操作。

## 12. 首版验收标准

1. 用户可以建立含清单型、计数型或两者混合的目标。
2. 用户可以在不创建待办的情况下勾选清单项或登记实际进展。
3. 系统能表达并正确计算全日制研究生综合素质模板的两组要求。
4. 活动名称既可从附件建议中选择，也可自由输入。
5. 页面能明确展示每项规则的当前值、要求值和缺口。
6. 编辑或删除原始记录后，所有汇总和达成结果同步更新。
7. 已归档目标仍可查看，模板更新不改变已有目标实例。
8. 账号间数据严格隔离，异常保存不产生部分数据。

## 13. 后续扩展边界

只有在实际使用证明有价值后，再考虑：

- 从信息或事务快捷创建进展记录；
- 从清单项创建待办，但保持松耦合；
- 目标模板复制、导出和共享；
- 截止日期与提醒；
- 证明材料和正式审核；
- 更丰富的数值聚合规则。

这些扩展不得改变“目标描述结果、待办描述下一步行动、进展记录描述已发生事实”的领域边界。
